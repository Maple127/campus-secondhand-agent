# B2 改动记录：强化搜索框 + 比价独立成功能

> **已归档（历史记录）。** 本文记录当时的改动过程与验证结果，
> 内容可能与当前代码不一致；现行设计请从 [文档索引](../README.md) 进入。

**背景**：B 阶段评测（[evaluation-findings.md](../evaluation-findings.md)）给出的行动顺序是
**先修检索、再把不需要 LLM 的能力从 agent 里拿出来**。本次落地这两项。

## 一、强化搜索框

### 1.1 修掉一个真实缺陷：价格筛选被静默丢弃

原实现里 `HomeController.home()` 已经接收 `minPrice` / `maxPrice`，
但调用的是：

```java
productService.searchOnSale(keyword, category, page, size);   // ← 价格参数没传
```

而 `searchOnSale` 内部把价格写死成 `null, null`：

```java
return productRepository.search(
        ProductStatus.ON_SALE.code(),
        query.getCategoryName(), query.getKeyword(),
        null, null, pageable);        // ← minPrice / maxPrice 恒定 null
```

**后果**：接口看起来支持价格筛选，实际完全不生效，且没有任何报错。
这是"半成品功能"最坏的形态 —— 有入参、有 UI 位置、就是不起作用。

**修复**：统一走 `ProductQuery`，新增 `searchOnSale(ProductQuery)` 重载，
旧签名保留为薄封装（避免破坏调用方）。

### 1.2 新增的搜索能力

| 能力 | 说明 |
|---|---|
| 价格区间 | `minPrice` / `maxPrice`，支持只填一端 |
| 排序 | 最新发布 / 价格升序 / 价格降序 |
| 条件保留 | 切换分类、翻页时都带上价格与排序，不会再丢 |
| 结果计数 | 展示"共 N 件" |
| 空结果引导 | 价格区间无结果时提示"放宽价格条件试试"并提供一键链接 |

### 1.3 数据库索引

```sql
CREATE INDEX idx_product_filter ON product(status, category_name, price);
```

对应搜索页的"状态 + 分类 + 价格区间"组合条件，以及比价取样。
由 Hibernate `@Index` 声明 + `DatabaseUpgrader` 幂等补齐。

### 1.4 这一项的评价值

评测里"条件筛选"一档：**搜索框 71% → agent 100%**。
搜索框输的原因就是没有价格区间 —— 它把「300 到 800」整句当关键词。
补上之后这类需求回到搜索框，**11ms、零成本**，
不需要再绕道 6.7 秒、每次 ¥0.015 的 agent。

## 二、比价从 agent 里拿出来

### 2.1 为什么要拿

`PriceComparisonService` 是**纯统计**（分位数、区间、结论），
不需要任何语言理解。但它此前只挂在 agent 后面，
于是"看这个价合不合理"必须走：模型推理 → 工具调用 → 6.7 秒 → ¥0.015。

**最有价值的能力被藏在了最慢的入口后面。**

### 2.2 新增的两类入口

| 入口 | 路径 | 用途 |
|---|---|---|
| 网页（HttpSession） | `GET /web/products/{id}/price-insight` | 商品详情页价格参考 |
| 网页（HttpSession） | `GET /web/price-insight?category=&condition=&price=` | 发布页定价建议 |
| Agent（双层令牌） | `GET /api/v1/products/price-suggestion` | agent 工具继续可用 |

**为什么网页不直接调 `/api/v1/**`**：那里走的是 agent 网关，
必须带 `X-Service-Token` 与 `X-Actor-Token`。浏览器只有 HttpSession cookie，
硬让它调 /api/v1 就等于把服务令牌下发到前端 —— 安全倒退。
因此开一组只依赖登录态的网页端点，**业务逻辑复用同一个 Service**。

### 2.3 前端组件

- `templates/fragments/price-insight.html` — 可复用片段
- `static/js/price-insight.js` — 渲染逻辑（区间条 + 中位刻度 + 事实行 + 解释 + 同类样本）
- `static/css/price-insight.css` — 样式

两个使用点：

| 位置 | 模式 | 行为 |
|---|---|---|
| 商品详情页 | `scope: 'product'` | 完整展示：区间条、中位、样本、偏高/合理/偏低 |
| 发布页 | `scope: 'publish', compact: true` | 选分类/成色、填价格 → 实时定价建议（防抖 400ms） |

**异步加载**：统计查询比页面渲染慢，同步渲染会拖慢详情页。
组件异步取数，**失败就整块隐藏**，绝不影响主流程。

### 2.4 发布页新增成色字段

定价参考按"分类 + 成色"收窄样本，因此发布表单补上了成色下拉。
`conditionLevel` 在实体、`ProductPublishCommand`、Controller 里本就支持，只是表单没收集。

## 三、过程中修的三个"数字误导"问题

这三个都不是崩溃性 bug，而是**会给出看起来合理、实则答非所问的数字**——
比报错更危险。

| # | 问题 | 后果 | 修复 |
|---|---|---|---|
| 1 | 分类名写错时静默放宽到全部分类 | 查「数码产品」（拼错）拿到全站均价，文案写着"参考全平台 N 件" | 分类不存在 → 明确返回"没有找到分类「X」" |
| 2 | 定价建议在分类无货时也放宽 | 给「服装鞋帽」定价，参考到全平台 19 件（含 1800 的电动车） | `suggestFor` 不放宽（`allowCategoryFallback=false`），宁可说样本不足 |
| 3 | 放宽范围后仍写"同类商品" | 用户以为是同类统计 | 放宽时文案改为"全平台商品（该分类样本不足，已放宽范围）" |

第 3 条是**单元测试发现的**：我写的 `productComparisonMayWidenAndSaysSo`
断言解释里要出现"放宽"，结果失败 —— 说明代码确实没标注。

> 设计原则：**放宽范围可以，但必须说出来。** 用户看到"参考 4 条同类商品"
> 和"参考 4 条全平台商品"，得到的结论完全不同。

### 4.4 评测复测（最重要的验证）

改动后重跑 30 条金标准任务：

| 类别 | 搜索框 | B 阶段 agent | B2 后 agent |
|---|---|---|---|
| 找东西 | 88% | 75% | **100%** |
| 条件筛选 | 71% | 100% | **100%** |
| 多步任务 | 33% | 83% | **100%** |
| 写操作 | 20% | 80% | 80% |
| 安全边界 | 100% | 100% | 100% |
| **总** | 63% | 87% | **97%** (29/30) |

唯一失败项 W03 是任务集自身缺陷（agent 正确地拒绝了不属于自己的商品）。

**但成本也上升了**：单次 ¥0.0153 → ¥0.0197，因为"换词重试"让模型多跑了一次往返。
这恰好说明**真正的解法是语义检索** —— 它能用一次请求替掉这几次试错。

> 复测过程中还踩到一个反直觉的坑：加了"搜不到就换词重试"后，
> **找东西升到 100%，条件筛选却从 100% 掉到 71%** ——
> 模型为了让结果非空，把用户的价格上限也一起放宽了，
> 「50 块以下的自行车」被回答成「捷安特 ¥350」。
> 最终按条件分支处理，详见 [评测结论 7.2](../evaluation-findings.md)。

## 五、已知限制

- 价格筛选是精确数值比较，未做"100 左右"这类模糊语义（属语义检索范畴）
- 排序只支持发布时间与价格，未支持"热度/距离"
- 发布页的定价建议需要先选分类（无分类的"全平台均价"参考意义不大，故不请求）
- 比价样本含"已售出"商品，可能拉低中位数（成交价与挂牌价混用，后续可分离）
- 网页端点未加访问频率限制，实际部署需补
- 找东西一档虽到 100%，但靠的是模型换词重试，**检索本身没有变强**；
  语义检索仍是更根本的解法
