# 品类词（product_type）：用标签解决"搜不到"

## 一、为什么做这件事

评测里 look​up 有一条稳定失败的任务：

> 用户搜「耳机」→ 平台在售《AirPods Pro 2代》→ **命中 0 条**

原因不是检索算法差，是**词汇缺口**：AirPods 的标题和描述里都没有"耳机"两个字。

我们在 B 阶段把这类失败"补"过一遍——让模型换词重试（「耳机」→「airpods」「蓝牙耳机」），
lookup 从 62% 提到 100%。**但那不是修好，是用模型算力兜底**：

| | 改造前 |
|---|---|
| 单次对话工具调用 | 2~3 次（试错） |
| 单次成本 | ¥0.0197（比 B 阶段前的 ¥0.0153 更高） |

原来的计划是上向量检索。后来改了主意，理由有二：

1. **"AirPods 是耳机"是一个事实，不是语义相似度。** 事实应该用词表表达，确定、可解释、可审核。
2. **买家是"想好了才搜"**（见 [评测结论](eval-findings.md) 的讨论）。
   用户不会搜「宿舍能用的小电器」这种运营位的说法，会搜「台灯」「耳机」「自行车」。
   既然意图明确，需要的是**词汇覆盖**，不是模糊匹配。

一句话：**把词汇缺口从"代码问题"变成"数据问题"。** 补一个别名是一行 SQL。

---

## 二、设计决策

### 2.1 单层标签，不做树

`数码电子 → 耳机`。只有一层，够用。

不做"大类 → 中类 → 品类"三层，是因为我们只有 22 件商品，三层树在这里只会增加维护成本。

### 2.2 匹配规则：**只允许"查询里含标签词"**

试过双向包含（查询含标签 **或** 标签含查询），实测会误召回：

```
查询「自行车」 → 返回《小牛电动车N1S》
原因：别名里有"电动自行车"，"自行车"是它的子串
```

| 规则 | 完全命中 | 误召回 |
|---|---|---|
| 双向包含 | 27/28 | 1 |
| **单向包含** | **28/28** | **0** |

单向的代价是"用户输入比标签短"时会漏（搜「收纳」但标签是「收纳箱」）。
解法不是放宽规则，而是**把短词写进别名**——每加一个词只是一行数据。

> 原则：**宁可漏，不可错。** 漏了用户换词还能找到；错了（搜自行车出来电动车）会直接失去信任。

### 2.3 别名用逗号分隔，不用 JSON

后台管理员编辑的是人，不是程序：

```
蓝牙耳机,airpods,苹果耳机,有线耳机,耳麦,tws
```

比 `["蓝牙耳机","airpods"]` 更好改、更不容易写坏。解析只有一个 split。

### 2.4 品类词可以为空

发布时不强制。**卡住发布比少一个标签更糟。**

缺失的品类由管理员后补；同时发布页会按标题自动猜一个并预选，卖家点确认即可。

## 三、数据模型

```sql
-- 词表（管理员维护）
CREATE TABLE product_type (
  id, category_id,      -- 挂在哪个分类下；NULL 表示全局通用
  name,                 -- 「耳机」← 商品上存的就是这个值
  aliases,              -- TEXT，逗号分隔
  sort_order, create_time
);

-- 商品上：一个字段
ALTER TABLE product ADD COLUMN product_type VARCHAR(32) NULL;
```

不做外键、不存 id：与项目既有的 `category` / `categoryName` 存储方式保持一致（denormalized），
好处是搜索和展示都不用 join，改名时用一条 UPDATE 兜。

## 四、三个使用点

| 位置 | 行为 |
|---|---|
| **搜索** | 先把查询翻译成品类词，命中就 `product_type IN (...)` **OR** 文本 LIKE；品类命中排在文本命中之前 |
| **发布页** | 选分类 → 加载该分类的品类词；输入标题 → 自动猜一个并预选（卖家用不着从 28 个词里找） |
| **管理端/REST** | `productType` 随商品返回，Agent 能据此解释"用户搜耳机，这件是耳机" |

搜索的 SQL 语义（`ProductRepository.search`）：

```sql
AND (
  :keyword IS NULL
  OR p.productType IN (:typeNames)          -- 品类命中
  OR LOWER(p.name) LIKE ...                 -- 文本兜底
  OR LOWER(p.description) LIKE ...
  OR LOWER(p.location) LIKE ...
)
ORDER BY CASE WHEN p.productType IN (:typeNames) THEN 0 ELSE 1 END,
         p.createTime DESC
```

**词表没覆盖的词，行为与改造前完全一致**（`typeNames` 传哨兵值，退回纯 LIKE）。
也就是说：这个改动**只会变好，不会变差**。

## 六、已知限制（重要的三条）

### 6.1 同一品类内不再细分

搜「线代」会同时返回《高等数学》——因为两本书的 `product_type` 都是"数学"。

单层标签的固有限制。要修就得把"线性代数"提成独立品类词，或者做两级标签。
**当前规模（22 件）不值得**，先记着。

### 6.2 覆盖率靠人工维护

词表 28 个词，能覆盖我们现在的 22 件商品。但真实用户的说法我猜不全。

缓解办法（**已实现**，见第十节）：记录搜索日志，
「搜了但没结果」的那份清单就是词表的采购清单。

### 6.3 比价并没有因此变准

原以为品类词能顺手把「数码电子价格区间 4.5 倍宽」修掉。**不能。**

按品类分，22 件商品落到 28 个品类上，**平均每类不到 1 件**——
而比价的最低样本是 3 条，按品类取样必然不足，全部退回按分类。

**这是数据量问题，不是设计问题。** 要等商品量起来（或做"品类族"合并）才有解。

## 七、运维：怎么加词

目前用 SQL（还没有管理界面，属于后续工作）：

```sql
INSERT INTO product_type (category_id, name, aliases, sort_order)
VALUES (2, '音箱', '蓝牙音箱,小音箱,音响', 90);
```

要点：
1. **别名里要放用户的说法**，包括简称、品牌、英文、错别字
2. **短词也要写**（标签「收纳箱」→ 别名加「收纳」）
3. 改完不用重启，服务端缓存 60 秒后自动生效

## 八、踩过的两个坑

### 8.1 零日期导致接口 500

Hibernate 建出来的 `create_time` 是 `datetime(6) NOT NULL` 且**没有默认值**。
用 SQL 直接 INSERT 而不写 `create_time` 时，MySQL 会写入零日期，
之后 JDBC 读到它就抛 `Zero date value prohibited`，表现是**接口 500**，
而且日志里看不出跟品类词有关。

修复：给列加默认值。

```sql
ALTER TABLE product_type
  MODIFY create_time datetime(6) NOT NULL DEFAULT CURRENT_TIMESTAMP(6);
```

### 8.2 JPQL 的 `IN ()` 是非法语法

没有命中任何品类时，`p.productType IN ()` 会直接报错。
解法是传一个不可能匹配的哨兵值（`__NO_TYPE__`），保证 SQL 始终合法。

## 十、搜索日志：词表的采购清单

词表是人写的，覆盖不全。与其继续猜用户会怎么叫东西，不如记录下来。

### 10.1 表结构

```sql
CREATE TABLE search_log (
  id, keyword, category,
  result_count,          -- =0 是最有价值的信号
  source,                -- web | agent
  actor,                 -- 用户名，便于识别重复搜索
  create_time datetime(6) default current_timestamp(6)
);
```

`create_time` 故意带默认值 —— 零日期的坑在 `product_type` 上已经踩过一次。

### 10.2 三个刻意的设计

**只记有关键词的搜索。** 打开首页没有关键词，那是浏览不是搜索，记下来只会淹没真正的信号。

**只记第一页。** 翻页会把同一个查询重复计数；`page != 0` 直接跳过。

**写日志失败不能影响搜索。** 用 `REQUIRES_NEW` 独立事务（主流程是只读事务，复用会报错），
整个写入包在 try/catch 里，失败只留一条 warn。用户来是为了找东西，不是为了让我们统计。

### 10.3 管理端页面

`/admin/search-log`（仪表盘上有入口，会显示"有 N 次搜索没有结果"）：

| 面板 | 用途 |
|---|---|
| 🔴 无结果的关键词 | **词表缺词** 或 **平台缺货** |
| 🟡 命中很少（1~2 件） | 有货但少，通常是供给问题 |
| 🔥 搜索最多 | 需求分布 |
| 🕒 最近搜索 | 带来源（🔍 搜索框 / 🤖 AI）与命中数 |

### 10.4 实测：agent 的重试会自动生产同义词

让 agent 搜「有没有吉他」，它连试了 4 个词：

```
吉他 → 0
吉他 → 0
民谣吉他 → 0
尤克里里 → 0
```

这 4 条全部进了日志。也就是说：
**agent 的试错行为本身就在替我们采集用户词汇**，而这些正是词表该收的同义词。

> 顺带暴露一个问题：缺货时 agent 仍会重试 4 次，白烧 token。
> 日志能区分"缺词"（同一词反复失败）和"缺货"（多个同义词都失败），
> 但 agent 当下分不出来 —— 这是后续可以优化的点。

### 10.5 怎么用这份日志

每周扫一眼「无结果」榜，三种情况：

| 情况 | 处理 |
|---|---|
| 平台有这件货，词表不认识这个说法 | 加别名（一行 SQL） |
| 平台确实没货，但很多人搜 | 运营问题：引导卖家发布 |
| 搜的是我们根本不卖的品类 | 忽略，或加"暂无此类商品"提示 |

### 10.6 验证

```
搜索「显示器」「吉他」「投影仪」→ 0 结果，全部进日志
搜索「耳机」「收纳箱」        → 命中 1，进日志但标绿
翻页 page=1                  → 不重复计数（总数停在 6）
agent 搜索                   → source=agent，actor=user01
管理端 /admin/search-log     → 四个面板正常渲染
```

## 十一、把"搜不到"变成入口 + 让 agent 少重试

搜索日志暴露出两件事：
**零结果的页面是把人赶走的**，**agent 对缺货的查询会反复换词**。分开处理。

### 11.1 零结果不再是一堵墙

以前首页搜不到只有一行字："暂无商品，点击右下角 ＋ 发布"。
现在按原因分三种说法，每种给不同的出路：

| 情况 | 页面说什么 | 给什么出路 |
|---|---|---|
| 词表**认识**这个品类，但没货（`TYPE_EMPTY`） | 「平台上还没有人挂这个品类」 | 看看同类目 + 发布 |
| 词表**不认识**这个说法（`NO_TYPE`） | 「可能是叫法不一样」 | 看看全部 + 发布 |
| 价格筛选筛没了 | 「这个价格区间没有商品」 | 清除价格条件 |
| 全站空 | 「这里还空着」 | 发布第一件 |

并且**底部给 4 件替代推荐**（优先同类目、其次全站最新）——
让用户在一次失败之后还能看到点东西，而不是面对空白离开。

实测（真实接口）：

```
搜「显示器」 → 平台还没人挂这个品类
             推荐：测试键盘 / 小米移动电源 / 罗技G304 / 机械键盘   ← 同类目
搜「投影仪」 → 可能是叫法不一样
             推荐：全站最新 4 件
```

`显示器` 是个漂亮的例子：词表里有这个品类，但没人挂货。
系统认得出这种差别，所以能说"没货"而不是"没听懂"。

### 11.2 日志里多一列：零结果原因

`search_log` 增加 `hint`（`NO_TYPE` / `TYPE_EMPTY`），管理端相应拆成两个面板：

| 面板 | 含义 | 怎么处理 |
|---|---|---|
| 🔴 词表不认识的说法 | 词汇缺口 | 补一个别名，一行 SQL |
| 🟠 平台没货的品类 | 供给缺口 | 运营去引导卖家发布 |

把这两件事混在一个列表里是没法行动的 —— 一个要改数据，一个要拉供给。

### 11.3 agent 的重试上限

实测搜「有没有吉他」，agent 连试了 4 个词：

```
吉他 → 0    吉他 → 0    民谣吉他 → 0    尤克里里 → 0
```

4 次后端请求 + 4 轮模型往返，全部空手而归。对一个**缺货**的查询，
第一次空就已经说明问题了。

现在 `search_products` 里加了一个**按轮次隔离的计数器**：

```python
MAX_EMPTY_SEARCHES = 2   # 允许换 1 次说法
```

- 第 1 次空 → 返回 `retries_left: 1`，提示"最多再换 1 种说法"
- 第 2 次空 → `retries_left: 0`，提示"停止换词，直接回答用户"
- 第 3 次 → **直接拦下，不再请求后端**，返回 `stop: true` 和试过的词

计数器放在 `tool_context` 创建的 `TurnSearchState` 里，**请求结束自动丢弃**，
所以上一轮的失败不会影响下一轮。中途搜到东西则清零（两段不相干的查询不该互相牵连）。

实测效果：

```
改造前：搜索 4 次
改造后：搜索 2 次，3.5s
答：「平台上暂时没有在售的投影仪，我换了「投影仪」「投影」两种说法都没搜到。
     换个类目逛逛…或者发布闲置」
```

重点是**回答变诚实了**：明确说"换了两种说法都没搜到"，
而不是含糊其辞或者继续无限重试。

### 11.4 顺手踩到的坑

跑验证脚本（30 个查询 × 2 遍）之后，日志被 60 条测试查询淹没，
真实信号完全看不见。

**这说明日志需要一个"排除测试流量"的机制**（比如给验证脚本带一个标记位）。
目前只是手工清理，属于已知欠缺。
