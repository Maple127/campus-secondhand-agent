# 已知限制

> 这一页汇总**没做的、做不好的、没验证的**事。
>
> 为什么单独成页：散在各篇末尾的限制，读者永远看不全；而"知道自己哪里不行"
> 恰恰是这个项目最想表达的东西。**下面每一条都对应一次真实的失败或一次没做的实验。**

## 一、压根没做

| 缺什么 | 影响 | 难度 |
|---|---|---|
| **部署** | 没有 Dockerfile、没有线上地址，只能本地跑 | 半天 |
| **站内消息** | 「联系卖家」是弹出手机号，聊完平台什么都记不到 | 3~5 天 |
| **出价单** | 议价只做到"给建议"，谈成得靠人线下聊 | 1~2 天 |
| **真实用户** | 158 件商品是脚本生成的，没有一条真实反馈 | —— |
| **通知** | 卖家看不到"有人出了价"，得自己去翻 | 1 天 |

## 二、做了但不够好

| 问题 | 现状 |
|---|---|
| **系统提示词太胖** | agent 每条请求固定支付 ~8k token（prompt + 13 个工具 schema）。E5 测出来这是最大成本项，比对话历史还大 |
| **工具集没按角色收窄** | 买家/卖家共用 13 个工具，靠后端归属校验兜底，而不是在工具层就分开 |
| **品类颗粒度太粗** | 「耳机」下既有 ¥45 有线耳机也有 ¥1150 头戴，四分位区间宽达 7 倍，"合理区间"意义有限 |
| **合并不了多步关联** | 「这个和那个哪个值」必须走 agent，快路径帮不上 |
| **用户无法选模式** | 快/深全自动，用户无感（WeKnora 是给两个显式模式） |

## 三、验证不足

| 缺口 | 为什么算缺口 |
|---|---|
| **评测只跑单次** | 同一配置三次跑出 87% / 83% / 97%，方差极大，结论对分布敏感；没做 pass^k |
| **重试的正收益没测出来** | E4 只证明"完全不可达时重试是纯损失"，瞬时故障场景没有假后端，测不了 |
| **长对话没有临界点** | E2 测到 30 轮约束还在，但多少轮开始丢？不知道 |
| **闸门的影响没量化** | E3 显示它省一次后端请求、耗 25 token，但没有后端请求埋点，"省了多少"是推断的 |
| **没有对抗测试集** | 注入防护只有 22 条手写用例，真实绕过率未知 |

## 四、结构性风险

| 风险 | 说明 |
|---|---|
| **间接注入拦不住** | 正则只能挡"长得像注入"的输入，用自然语言慢慢引导挡不住 |
| **工具结果没有出处标记** | 模型分不清"这条数据来自后端"还是"来自卖家描述里的伪造字段" |
| **单实例** | 能力令牌与指标都在进程内存，横向扩展需要换存储 |
| **前端直连 8090** | 需要 CORS；生产应改为 Java 反向代理 `/agent/**` |

## 怎么用这一页

**面试时：** 被问到不会的，先翻这里。**有准备地说"这块我没做"，比临场编一个方案安全**——
编的撑不过两个追问。

**写简历时：** 这一页上的数字一个都不要写成"已解决"。
比如不要写"实现了高可用重试"，因为 E4 证明完全不可达时它是负收益。

**做规划时：** 每补一条，就把它改成"已解决"并写明是怎么验证的。
判据是**有可复现的实验**，不是"写完了代码"。
