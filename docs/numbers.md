# 数字口径

> 这一页只回答一件事：**这个项目里的数字，哪些能对外说，哪些不能。**
>
> 写简历、面试、做 PPT 之前先看这里，别让一个撑不住的数字毁掉整份材料的可信度。

## 一、可以引用（附口径）

| 数字 | 值 | 口径（必须一起说） |
|---|---|---|
| 端到端成功率 | 搜索框 63% / AI 助手 87% → 97% | 30 条金标准任务 × 3 组对照，**单次运行** |
| 单轮检索 | 搜索框 **88% / 10ms**；agent 100% / 7.3s | 同上；因此**这一档搜索框更好** |
| 多步任务 | 33% → 100% | 同上，6 条任务（样本小） |
| 写操作 | 20% → 80% | 同上，5 条任务 |
| 品类词召回 | 66.7% → 100% | 30 条标注查询，**同一份数据、同一时刻**只改一个开关 |
| 显式路由效果 | 延迟 −48.6%、输入 token −74.7% | 6 条检索问句；剔除 1 条兜底样本后为 −58.0% / −96.9% |
| 上下文压缩 | 12 轮 −31.6%；30 轮 **−35.2%** | 固定剧本对话，输入 token 口径（不是成本） |
| 空结果闸门 | token **+25**，省 1 次后端请求 | 3 次运行结果完全一致 |
| 后端全挂时重试 | 多花 **5.0 秒**，零收益 | 故障注入，后端指向死端口 |
| 单元测试 | 后端 50 / agent 115 | 全部脱网，Mockito 与 Fake 模型 |

## 二、不能这样写

| 别写 | 为什么 |
|---|---|
| 「成功率 97%」不加任何限定 | 单次运行；同一配置三次跑出过 **87% / 83% / 97%**，方差极大 |
| 「性能提升 700 倍」 | 那是**搜索框本来比 agent 快**，不是你的优化成果。偷换对比，面试官最反感 |
| 「幻觉率 0%」 | 我们没测过幻觉，只测了任务成功率 |
| 「重试提升了可靠性」 | 故障注入显示：后端完全不可达时重试是**纯损失** |
| 「压缩降本 35%」 | 压缩本身也调用模型生成摘要，35% 是**净效果的上界**，不是成本降幅 |
| 「约束保留 100%」 | 是**单次人工核对**，且 30 轮那次次要细节确实丢了 |
| 「高并发 / QPS」 | 只有一个乐观锁场景，没有压测 |
| 「已部署」 | 只有本地运行，没有 Dockerfile 和线上地址 |
| 「RAG / 向量检索」 | 做的是品类词表 + LIKE，不是向量检索 |
| 「微服务 / Redis / 消息队列」 | 没用过，问了就露 |

## 三、面试时主动说

比被追问出来强得多：

1. **30 条任务偏少**：单分类只有 4~8 条，一条任务的成功或失败就是 12~25 个百分点。
2. **单次运行**：没做多次取均值，也没做 pass^k（连续 k 次都成功）。
3. **任务分布是人设的**：如果真实用户里检索型需求占九成，agent 的整体价值会低得多。
4. **评测只认首次检索入参**：对"换词兜底"这类合理行为不友好。
5. **压缩的净收益是上界**：摘要用同一个主模型生成，成本没从分子里扣。

## 四、写简历时的推荐句式

> 自建 30 条任务 × 3 组对照（程序化判分），发现单轮检索用 Agent 是负收益（7.3 秒 vs 10 毫秒），
> 据此实现显式三路路由，简单检索延迟降低 48.6%、输入 token 降低 74.7%。

**先写"我判断了什么"，再写"因此提升了多少"**——前者可信且显水平，后者一戳就破。
