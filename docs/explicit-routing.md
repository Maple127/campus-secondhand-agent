# 显式策略路由

> 状态：**已实现并实测**。三路路由 + 度量 + 消融实验（E5）。

## 为什么做

之前的分流是**隐式**的：模型自己决定调不调工具、调几次。

这带来三个问题：

1. **不可观测**——事后没法回答"这次请求走了哪条路"
2. **不可控**——一句"有没有耳机"也可能触发多轮工具调用
3. **不可测**——想优化某条路径，却分不清哪次走了哪条

更关键的是：评测早在两轮前就告诉我们**纯检索场景用 agent 是负收益**，
但那个结论一直只写在文档里，产品上没有任何机制去落实它。
显式路由就是把那个结论变成代码。

## 三条路，不是五条

参考实现（Adaptive-RAG 电商客服）有 5 条：`DIRECT / SINGLE / MULTI / AGENT / REFUSE`。
它是知识库客服，有"多跳政策问题"这种真实场景。

我们**没有**：商品检索不存在"多跳"的概念，只有一个查询词加若干筛选项。
硬套五条就是为架构而架构。所以只留三条：

| 策略 | 触发条件 | 执行方式 |
|---|---|---|
| `REFUSE` | 注入、越权、明显超范围 | 直接拒绝，不进入任何业务路径 |
| `FAST` | 抽得出检索词的单一请求 | 规则解析 → 后端检索 → 一次模型调用 |
| `AGENT` | 写操作 / 多步 / 长输入 / 抽不出词 | 完整 ReAct 循环 |

## 规则是地板和天花板

设计取自 `_research/Adaptive-rag-2/app/retrieval/adaptive.py`：

> 先算规则结论，再让模型判断，但**规则可以否决模型**。

那边有两处强制覆盖，都很值得学：

- 没订单号的政策问题，模型判成 AGENT → 用规则（省一次工具调用）
- 出现订单号、规则判 AGENT → 用规则（不许模型跳过必需的工具）

我们这一步**完全用规则，不调模型**，原因：

1. 路由本身调一次模型，就抵消了 FAST 省下的时间
2. 规则是纯函数，可以脱网测（33 条用例，无需 API Key）
3. 判错了有兜底

第 3 点最重要，见下节。

## 兜底：宁可慢，不能答错

FAST 只在**四种情况**下返回结果：

1. 抽得出检索词
2. 后端检索**返回了商品**
3. 模型生成成功
4. 生成的文本非空

其余一律 `return None`，退回去走 agent：

| 情况 | 为什么退回 |
|---|---|
| 抽不出关键词 | 硬查会查错 |
| 检索为空 | 零结果的替代推荐与话术都在 agent 侧，不想写两份 |
| 检索报错 | 错误处理链路在 agent 侧更完整 |
| 生成失败/空文本 | 宁可多花一次往返，也不能返回空 |

实测验证过这条路真的会触发：问「300 以下的显示器」（平台没有），
快路径检索为空 → 自动退回 agent，两列数据完全一致（见 `docs/ablation.md` E5）。

## 可观测

每次响应都带两个字段：

```json
{
  "reply": "...",
  "strategy": "FAST",
  "routeReason": "单一检索请求"
}
```

SSE 流里每个事件也带 `strategy`。

`/api/metrics` 里有五个计数器：

| 计数器 | 含义 |
|---|---|
| `route_refuse` | 被拒绝的请求 |
| `route_fast` | 判为快路径的次数 |
| `route_fast_ok` | 快路径真正答出来的次数 |
| `route_fast_fallback` | 快路径答不了、退回 agent 的次数 |
| `route_agent` | 走完整 agent 的次数 |

`route_fast_ok / route_fast` 就是快路径的**命中率**——这是判断路由规则是否靠谱的核心指标。

## 实测（E5）

| 条件 | 平均延迟 | 平均输入 token |
|---|---|---|
| 全走 agent | 2,451ms | 8,990 |
| 快路径 | **1,261ms** | **2,270** |
| | −48.6% | −74.7% |

剔除那条兜底样本后：**−58.0% 延迟，−96.9% 输入 token**。

详细明细与异常解释见 `docs/ablation.md` E5。

## 一个意外发现

走 agent 时，**每一句"有没有耳机"的输入 token 都在 8,000 以上**。

原因：agent 的 system prompt + 13 个工具的 schema 全量进上下文，
不管问题多简单，这 8k 都要付。

这也解释了压缩为什么只省 35%——压缩动的是**对话历史**，
而这 8k 是**固定开销**，压缩碰不到。

**结论：想再降成本，最大的杠杆是瘦身系统提示词和工具集，不是压缩历史。**

## 已知不足

| 不足 | 影响 |
|---|---|
| **规则是启发式的** | "改成"这种词既可以指改价格也可以指改描述，规则只能用保守判断 |
| **用户无法选择模式** | 目前全自动。WeKnora 是给"快问快答/深度推理"两个显式模式，用户可感知 |
| **FAST 不做多步关联** | "这个和那个哪个值"必须走 agent，快路径帮不上 |
| **没有命中率监控告警** | `route_fast_fallback` 涨了没人知道 |
