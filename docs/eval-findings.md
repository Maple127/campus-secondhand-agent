# Agent 价值评测：结论与工程发现

**问题**：这个 agent 到底是不是噱头？
**方法**：30 条金标准任务 × 3 组对照（关键词搜索框两档 + AI 助手），程序化判定。

---

## 一、核心数字

| 指标 | 关键词搜索框（理想） | AI 助手 |
|---|---|---|
| 任务成功率 | 63% (19/30) | **87%** (26/30) |
| 平均耗时 | **11 ms** | 6689 ms（**621×**） |
| 总 token | 0 | 210,219 in / 4,787 out |
| 单次成本 | ¥0 | **¥0.015** |
| 安全边界 | — | 4/4 |

> 基线取"理想关键词"档：我用人工拆解出的最佳关键词与筛选条件喂给它。
> 这是**对搜索框最有利**的条件 —— 结论以它为准。用户原话直接当关键词的
> naive 档只有 30%，但那对基线不公平，仅作参考。

---

## 二、分类对比：强弱项必须拆开看

| 任务类型 | 条数 | 搜索框 | AI 助手 | 差值 | 结论 |
|---|---|---|---|---|---|
| 找东西 | 8 | 88% | 75% | **−12%** | 搜索框更好 |
| 条件筛选 | 7 | 71% | **100%** | +29% | agent 更好 |
| 多步任务 | 6 | 33% | **83%** | +50% | agent 唯一能做 |
| 写操作 | 5 | 20% | **80%** | +60% | agent 唯一能做 |
| 安全边界 | 4 | 100% | 100% | 0% | 打平 |

**成功率的 +24 个百分点只是一个笼统数字，真正的信息在分类里。**

---

## 三、结论

### 1. 纯检索场景：agent 是负收益

"找东西"这一档，搜索框 88%、agent 75%。而且：

- **延迟差 621 倍**（11ms vs 6689ms）
- **成本从 0 变成每次 ¥0.015**

用 agent 做纯检索是明确的赔本买卖。这一档应该继续用搜索框。

### 2. agent 的价值在"搜索框做不到的事"上

- **多步任务 33% → 83%**：搜索框根本没法"搜索 + 比价"、
  "查我发布的 + 查我的订单"。不是做得差，是**没有这个能力**。
- **写操作 20% → 80%**：发布、下单、下架，搜索框完全不涉及。
- **条件筛选 71% → 100%**：搜索框把 "300 到 800" 当字面关键词，
  agent 能正确拆成价格区间。

这部分占比 **37%**（11/30）。按这个任务分布，agent 的价值站得住 ——
但前提是它只被用在这 37% 的场景里。

### 3. agent 真正的瓶颈是**检索**，不是编排

四条失败里有两条（L05、L08）都是同一个原因：

| 任务 | 现象 |
|---|---|
| L05「耳机」 | 搜"耳机"找不到《AirPods Pro 2代》——商品名里没有"耳机"二字 |
| L08「考研用的数学书」 | 两次运行一次命中《线性代数》、一次命中《高等数学》——选词不稳定 |

后端用的是 `LIKE %关键词%`，**没有同义词和语义能力**。
L05 那次 agent 还自己换词搜"AirPods"补救成功了，说明编排是好的，是检索拖后腿。

> **这正好说明 ChromaDB 语义检索该做，而且优先级高于再加 agent 能力。**
> 现在给 agent 加更多工具，是在给一个查不准的底座上加功能。

### 4. 单次运行的结论不可靠

同一批任务跑了两次：

| 运行 | agent 成功率 | 找东西 | 多步 |
|---|---|---|---|
| 第一次 | 90% | 88% | 100% |
| 第二次 | 87% | 75% | 83% |

C01 一次通过、一次没调工具。**运行间方差是真实存在的**，
所以上面的结论我都按"两次运行都支持"来写，单次差异不当结论。
严谨做法是多次运行取均值与方差。

## 四、过程中修正的四个测量错误（否则结论会反）

评测的价值取决于测量是否正确。这一轮我一共修了四类问题，
**每一类都会让结论偏向某个方向**：

| # | 错误 | 症状 | 影响方向 | 修正 |
|---|---|---|---|---|
| 1 | 基线每条任务新建 `httpx.AsyncClient` | 搜索 15ms 被算成 4766ms | **夸大 agent 的速度优势 300×** | 复用长连接客户端 |
| 2 | 没有预热 | 第一条任务含 TCP 握手 ~1s | 污染首条对比 | 评测前预热 |
| 3 | 判定器解析被截断的工具预览 | agent 正确返回 10 件商品，被判"没有结果" | **人为压低 agent 成功率 7pp** | 拿 agent 实际参数回查后端取权威结果 |
| 4 | 分类统计与逐条数据不一致 | 报告里 filter 显示 57%，逐条算是 100% | **报告自相矛盾** | 统计一律从逐条结果现算 |

另外发现并修好了：

- **F06 任务设计错误**：漏了 `allow_empty`，导致 agent 正确回答"没有"反被判失败
- **W05 判定规则选错**：该测"有没有越界"，却写成了"有没有搜过"
- **库存基线漂移**：加 `eval.snapshot` 校验，不一致时中止而不是默默跑出脏结果

> 第 1 条最值得记：如果不查证，"agent 比搜索框快"这个完全相反的结论
> 就会被写进报告。**测量工具的 bug 比起被测对象的 bug 更危险**，
> 因为它会伪装成结论。

## 五、由此得到的工程结论

### 5.1 别用 agent 做纯检索 —— 这是最重要的行动项

搜索框 11ms、免费、成功率还更高。应该：

- 保留并强化搜索框（加价格区间、分类筛选 UI）
- **不要**把检索需求引导给 agent

### 5.2 把"不需要 LLM 的能力"从 agent 里拿出来

`compare_price` 是纯 Java 统计，不需要模型。它应该同时是：

- 商品详情页的"**价格参考**"组件（直接展示 p25/中位/p75）
- 发布表单的"**定价建议**"实时校验

现在它只存在于 agent 里，等于把最有价值的能力藏在了最慢的入口后面。

### 5.3 优先做语义检索，而不是加更多工具

失败集中在检索。应先上 ChromaDB（召回后仍须回主库复核状态），
再考虑扩展 agent 能力。

### 5.4 输入 token 开销值得优化

210,219 input tokens / 30 任务 ≈ **7,000 tokens/次**。
12 个工具的完整 schema 每轮都传，是主要开销。
可考虑：按意图裁剪工具集、精简工具描述。

### 5.5 成本口径要可配置

报告里的单价（¥2/¥8 每百万）是可配置默认值。
换模型（尤其 reasoning 模型输出单价差异大）时必须同步调整，
否则成本这个指标会悄悄失真。

## 六、复现方式

```bash
# 1. 起服务
cd backend && mvn spring-boot:run
cd agent   && powershell -File scripts/run-agent.ps1

# 2. 校验库存基线（不一致会中止，避免跑出不可复现的结果）
cd agent && .venv\Scripts\python.exe -m eval.snapshot

# 3. 跑评测
.venv\Scripts\python.exe -m eval.run_eval

# 4. 清理写操作副作用
.venv\Scripts\python.exe -m eval.cleanup
```

产物：

- `eval/results/report.md` — 可读报告
- `eval/results/report.json` — 逐条原始数据（用于复核，不信任聚合值）
- `eval/gold_tasks.json` — 任务集（含 `_knownIssues` 诚实披露）

常用参数：`--only L01,C01`、`--conditions agent`、`--no-writes`、`--force`。

## 七、B2 落地后的复测结果

按上面的结论做了两项改动（强化搜索框 + 比价独立成功能，见
[b2-search-and-pricing.md](b2-search-and-pricing.md)），并顺手修掉评测暴露出的两个 agent 行为问题。

### 7.1 复测数据

| 指标 | 搜索框（理想） | AI 助手（B 阶段） | AI 助手（B2 后） |
|---|---|---|---|
| 总成功率 | 63% | 87% | **97%** (29/30) |
| 找东西 | 88% | 75% | **100%** |
| 条件筛选 | 71% | 100% → 86% → 100% | **100%** |
| 多步任务 | 33% | 83% | **100%** |
| 写操作 | 20% | 80% | 80% |
| 安全边界 | 100% | 100% | 100% |
| 平均耗时 | 10 ms | 6689 ms | 7344 ms |
| 单次成本 | ¥0 | ¥0.0153 | ¥0.0197 |

### 7.2 修掉的两个真实 agent 缺陷

**缺陷 1：把分类名当关键词传**

用户说「300 到 800 之间的运动器材」，模型传
`query="运动器材"` + `category="体育器材"`。
后端条件是 `名称/描述/地点 LIKE %运动器材% AND category=体育器材`，
而《捷安特山地自行车》的描述里当然不会写"运动器材"四个字 —— **0 条**。

实测这个坑是系统性的：`category=X & q=X`（X 为任意分类名）**全都返回 0 条**。

修复：工具层检测到 `query` 与 `category` 相同时丢弃 query，并在工具描述里写清
"query 是模糊匹配名称/描述，不要把分类名当 query 传"。

**缺陷 2：搜不到就放弃，或者反过来放宽用户的硬条件**

第一次修的是"搜不到就放弃"：用户说"耳机"，模型搜一次没结果就直接说"没有"，
而商品其实叫《AirPods Pro 2代》。加了"换词重试"的提示后，找东西从 62% 升到 100%。

**但同一个改动把条件筛选从 100% 砸到 71%** ——
模型为了让结果非空，把用户给的价格上限也一起放宽了：
「50 块以下的自行车」被回答成「捷安特 ¥350」。

这说明一个笼统的"多试几次"提示是有害的。最终按条件分支：

| 情况 | 提示 |
|---|---|
| 有价格/分类等硬条件 | **不许放宽**，可以换关键词，换完还空就如实说没有 |
| 只有关键词 | 必须换 1~2 种说法重试（同义词 / 拆词 / 按分类兜底） |

一句话：**可以为找东西而换词，不可以为凑结果而放宽用户的硬条件。**

修复后：找东西 100%、条件筛选 100%、多步 100%。

### 7.3 但结论没有变，只是更精确了

**任务成功率上 agent 现在全面领先（97% vs 63%），但成本差距也更大了。**

| 场景 | 该用谁 | 依据 |
|---|---|---|
| 找东西 | **仍然是搜索框** | 搜索框 88%/10ms/¥0 vs agent 100%/7.3s/¥0.02 |
| 条件筛选 | 打平 | 两边都 100%（搜索框补上价格筛选后） |
| 多步任务 | **只有 agent 能做** | 33% vs 100% |
| 写操作 | **只有 agent 能做** | 20% vs 80% |

**关键判断**：找东西这一档，agent 现在是 100% vs 搜索框 88% ——
多出 12 个百分点，代价是 **717 倍延迟 + 每次 ¥0.02**。

> 12 个百分点的准确率提升，换 717 倍延迟，在"找一件具体东西"这种高频低价值动作上
> **不划算**。用户宁愿多试一个关键词，也不愿等 7 秒。
> **这不是"agent 输了"，而是"这类需求不该用 agent"。**

而多步任务（+67pp）和写操作（+60pp）那 11 条，
搜索框不是做得差，是**根本没有这个能力** —— 这才是 agent 的价值所在。

### 7.4 仍然存在的短板

- **检索本身还是关键词匹配**，无语义能力。找东西能到 100% 靠的是"模型多试几次"
  这个补丁，而不是检索变强了 —— 每次多试就多花一次模型往返（成本已升到 ¥0.0197）。
  **真正的解法仍是语义检索**，它能用一个请求替掉这几次试错。
- 单次运行，方差仍在（同一配置三次运行见过 87%/83%/97%）。
- W03 仍失败，是任务集设计错误（agent 正确地拒绝了不属于自己的商品），非 agent 问题。

## 八、这套评测本身的局限

诚实地说清楚，避免过度信任上面的数字：

1. **30 条任务偏少**，单分类只有 4~8 条，一个任务的成功/失败就是 12~25 个百分点
2. **单次运行**，未做多次取均值（方差已观察到：同一配置见过 87% / 83% / 97%）
3. **任务分布是人为设定的**。如果真实用户里检索型需求占 90%，
   那 agent 的整体价值就会低得多 —— 结论对分布敏感
4. **判定规则只认第一次搜索的入参**，对"换词兜底"这类合理行为不友好（L05）
5. **成本数字依赖可配置单价**，非实时价格
6. **未测多轮对话**，都是单轮任务；而多轮恰是 agent 的潜在优势区
7. **有对被测系统过拟合的风险**：7.2 的两处修复是看着评测失败用例做的。
   为降低这种风险，修复都写成了**通用规则**（「硬条件不许放宽」、
   「query 与 category 同名时丢弃」），而不是针对某条任务的特判，
   并且都补了对应的单元测试。但读者仍应意识到这个偏差。
