## 一、为什么需要 Agent

| 会被追问 | 我们的答案 | 证据 | 状态 |
|---|---|---|---|
| 这个功能为什么不能写死成工作流？ | 因为请求跨度大。单轮检索用搜索框（10ms），多步任务（搜→改词→再搜→比价）和写操作必须有模型参与决策 | 30 任务 × 3 组对照：单轮 88% vs 100%；多步 33% vs 100%；写操作 20% vs 80% | ✅ |
| 那为什么不全都交给 Agent？ | 因为评测显示纯检索场景 Agent 是**负收益**：慢两个数量级（7.3s vs 10ms），成本更高，成功率只高 12 个点 | 同一次评测的 lookup 类目 | ✅ |
| 你怎么证明"该用/不该用"的边界在哪？ | 按"是否需要多步、是否要写"切分。据此把比价从 Agent 里抽成独立组件 | `PriceComparisonService` 与 agent 工具并存，网页端不依赖 agent | ✅ |

## 四、上下文与记忆

| 会被追问 | 我们的答案 | 证据 | 状态 |
|---|---|---|---|
| 上下文怎么管？ | 按 **token 预算**触发压缩，不按轮数（一句"嗯"和一段长描述差十倍） | `app/memory.py` | ✅ |
| 压缩后会不会丢关键约束？ | 摘要提示词**显式要求保留**：预算上限、排除条件、已完成操作、待办。只按时间删消息一定会丢 | `tests/test_memory.py::test_summary_prompt_asks_to_preserve_constraints` | ✅ |
| 压缩会不会把当前轮也压掉？ | 不会。`split()` 从最后一条 HumanMessage 起全部保留 | `test_split_never_cuts_current_turn` | ✅ |
| 有挂起的确认时能压缩吗？ | 不能。interrupt 载荷引用了具体消息，改写会让恢复对不上。`state.next` 非空时跳过 | `AgentRunner._maybe_compress` | ✅ |
| 压缩省了多少 token？ | 12 轮对话输入 token −31.6%，末 3 轮 −43.3% | `docs/ablation.md` E2 | ✅ |
| 压缩本身花多少 token？ | **压缩复用主模型，所以压缩也要花钱**。用便宜模型会更省，但引入第二个模型的配置成本 | —— | ⬜ |
| 长对话里约束还保得住吗？ | 30 轮后核心约束全保留，次要细节（"落地灯不推荐"）丢失；单次人工核对 | `docs/ablation.md` E2 | 🟡 |

## 五、工具调用与容错

| 会被追问 | 我们的答案 | 证据 | 状态 |
|---|---|---|---|
| 工具调用失败怎么重试？ | 只重试**暂时性故障**：超时、连接失败、502/503/504。指数退避 + 抖动（防多个工具同频重试打垮后端） | `app/backend.py::_request` | ✅ |
| 4xx 为什么不能重试？ | 4xx 是业务结论（商品已售出、没权限），重试一万次结果一样；写操作还可能被执行两次 | `test_does_not_retry_on_400` | ✅ |
| 重试几次？ | 默认 2 次。耗尽后归为 504 并给用户可读文案，不把 httpx 异常抛给模型 | `test_exhausts_retries_and_reports_504` | ✅ |
| 重试的收益有多少？ | 故障注入：后端全挂时重试 **纯损失 +5.0s**；瞬时机理未验证 | `docs/ablation.md` E4 | 🟡 |
| 后端整个挂了会怎样？ | 实测优雅降级：用户看到"后端服务暂时不可用（504），稍后再试" | `docs/ablation.md` E4 | ✅ |

## 附：这张表怎么用

- 面试前不要背"答案"列，背**证据**列。有文件、有数字的才说得响。
- 空白格不要试图临场编。**说"这块我没做"比编一个方案更安全**——面试官往下问两句就露馅。
- 每补一个 ⬜，就回来把它改成 ✅ 并填上可复现的证据路径。
